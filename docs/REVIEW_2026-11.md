# Agency Atlas: full review, November 2026

Written 2026-11-25. This is a review only: no app code was changed. Everything below is a recommendation for you to approve or skip.

**Update 2026-11-25:** the owner approved #1–#3. They are built: paged reads past the 1,000-row limit, the lead refresh in the background, and the "Spending & limits" card on Data Safety (see `docs/PROJECT_HISTORY.md`). ## The short version

Atlas is in good shape where it matters most. The security rules hold (1,239 database break-in checks pass), all 640 automated tests pass, the production build works, and there are no known security holes in the 7 add-on packages it uses. Monthly running costs are modest: about $45 fixed, plus AI and DataForSEO usage that is capped.

The main problem isn't money. The app grew very fast (36 database updates, 55 screens and 9 AI helpers in about three weeks), and it now has more doors than your team needs. Some screens are empty sample shells once real data is on. There are three ways to fill an audit, two AI tools that draft work orders, and five separate spending caps on four screens. One correctness issue needs a quick look, and one slowdown hits whoever opens Home or Sales first each hour.

**My advice: spend the next 2–3 weeks finishing, trimming and measuring, not adding.** Then grow the developer helper out of BizToad, which already does most of the hard part.

## The developer helper: recommended path

**Build on BizToad; don't create separate bots.** BizToad already does the hard parts safely:
- It answers per role.
- It gets only the facts that person's login can read (the database decides).
- It is capped per person and rate-limited.
- It has no tools: it can't send, change or delete anything.
- It hides money from non-owners.
- It codes client names before anything reaches the AI.

A second bot would mean a second copy of all of that to keep safe.

"Customizable" should mean each person can shape how the helper talks to them and what it focuses on. It should **not** mean giving it new powers. Stages:

**Stage 0: use what exists ($0, about an hour).**
Give the developer's BizToad their own role guide and their personal goals as extra facts. Both already exist since 0036. Then it can answer "what should I focus on this week?" from what you and the managers set.

**Stage 1: "My helper" settings, per person (1–2 days, one small database update).**
On the Account page, each person sets:
- **Focus:** which of their clients or work types to prioritize.
- **Style:** short or detailed, checklist or prose.
- **Standing instructions:** up to ~500 characters, e.g. "I do WordPress and local SEO; give me step lists".
- **Quick buttons:** 3–5 saved questions, e.g. "What's due today?", "Summarize the review notes on my open work orders".

The safety rules for these settings:
- The settings are **only for that person**: they can read and edit their own row only, enforced by the database.
- You and the managers can see them and reset them.
- They pass the same "no passwords or keys" check as Kit pages.
- They are sent to the AI as preferences inside the existing rules. They can't unlock data or add tools.

Cost: same per-person cap.

**Stage 2: hand-off to coding (1 day).**
Developers do the actual coding in Claude Code, not in Atlas. Merge the existing "Work prompt" helper into BizToad as a button: **"Make a Claude Code prompt for this work order"**. It writes a copy-ready prompt from the work order, its steps and review notes (with client names coded). Atlas stays the "what and why"; Claude Code does the "how". Nothing is sent automatically.

**Stage 3, optional: saved notes (1 day).**
A person can tap "Save this" on an answer to keep it as a pinned note the helper sees next time. Nothing is remembered automatically. Each person sees and deletes their own notes.

**Not recommended:**
- giving the helper write access, tools, or a GitHub or GoHighLevel connection (this breaks rules 1 and 5);
- separate AI keys per developer;
- hosted "agent" services.

They add cost and risk for little gain at your size.

**Before Stage 1:** do recommendation #4 (cheaper model for BizToad). Each developer's $5 then covers several hundred questions instead of about 100.

## Appendix: read-only usage queries (Supabase → SQL Editor)

Each query only reads. They group by feature or role and never show names. Run them one at a time.

```sql
-- 1. AI spending by helper, last two months
select date_trunc('month', created_at)::date as month, feature,
       count(*) as requests, round(sum(cost_usd), 2) as usd, round(avg(cost_usd), 4) as avg_usd
from public.ai_usage
where created_at >= now() - interval '60 days'
group by 1, 2
order by 1 desc, usd desc;
```

```sql
-- 2. Every spending cap side by side
select (select monthly_budget_usd from public.ai_settings where id = 1) as ai_budget,
       (select monthly_usd from public.toad_settings limit 1)          as toad_total,
       (select per_person_usd from public.toad_settings limit 1)       as toad_per_person,
       (select monthly_usd from public.audit_settings limit 1)         as audits_month,
       (select weekly_usd from public.audit_settings limit 1)          as audits_week,
       (select monthly_usd from public.scout_settings limit 1)         as scout_month,
       (select monthly_usd from public.watch_settings limit 1)         as watcher_month;
```

```sql
-- 3. DataForSEO-side spending recorded this month
select 'audits' as what, round(coalesce(sum(usd), 0), 2) as usd from public.audit_spend where at >= date_trunc('month', now())
union all
select 'scout', round(coalesce(sum(usd), 0), 2) from public.scout_spend where at >= date_trunc('month', now())
union all
select 'watcher', round(coalesce(sum(coalesce(actual_usd, est_usd)), 0), 2) from public.watch_runs where created_at >= date_trunc('month', now());
```

```sql
-- 4. Which features are used: rows added per table (counts only)
select relname as table_name, n_live_tup as rows_now, n_tup_ins as rows_added_since_stats_reset
from pg_stat_user_tables
where schemaname = 'public'
order by n_tup_ins desc;
```

```sql
-- 5. Who signs in, by role (counts only)
select tm.role, count(*) as people,
       count(*) filter (where u.last_sign_in_at > now() - interval '7 days') as signed_in_last_7_days
from public.team_members tm
join auth.users u on u.id = tm.user_id
group by tm.role
order by tm.role;
```
